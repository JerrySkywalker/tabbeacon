# TabBeacon v0.8.0 candidate notes

These notes describe the current development candidate. v0.8.0 has not been
published or approved for production adoption. The current public release is
v0.7.3.

## Candidate changes

- Per-provider presentation preferences can inherit global defaults or use
  explicit admitted modes. Preview and Apply are separate operations in the
  CLI, wizard, and Control Center. Saving a setting does not prove that the
  current terminal has changed; visible output settles on the next owned event
  or when the old tab closes.
- Codex keeps its literal `codex` launch and capability-based Hook admission.
  The candidate handles an admitted structured `Interrupt` event without
  inferring backend failure from terminal text or conversation content.
- The admitted Agy 1.1.19 title callback supports explicit preserve-native.
  Agy gains no tab-color, progress, animation, or abnormal-outcome capability.
  Narrow admission work for actual 1.2.7 is Owner-authorized, with compatibility
  and real title callback/preserve-native qualification still pending.
- Cursor's isolated candidate integration keeps the literal `agent` command,
  uses owned project Hooks, and writes only tab color in strict color-only mode.
  Its original title remains under Cursor control.
- Portable configuration export/import supports preview, drift refusal, and
  ownership-aware recovery. The [bilingual terminology](terminology.md) and
  [configuration guide](configuration.md) define the new terms and boundaries.

## Qualification still required

The isolated tests and owned Windows Terminal fixtures do not establish general
real-provider support. Fresh original-command mixed Cursor/Codex/Agy isolation,
and final changed-title visible transitions still require their applicable
acceptance evidence. Owner already accepted the pinned release single-Codex
Interrupt/recovery/completion/normal-exit test and the separate dual-Cursor
visible observation; their bounded original proofs are retained without repeat.
In the audited Codex 0.157.1 original-command Hook path, Warning, Failed and
the original Issue #116 HTTP 404 have no authoritative signal. The Owner approved
this as a v0.8.0 known limitation: these errors may not update tab state, detection
is not PASS, and #116 remains OPEN. This does not claim that all Codex paths or
future versions are unsupported. A new lawful structured signal can enable the
actual fix. Neither an
app-server notification nor a synthetic event is a substitute for that Hook
signal. See [supported coding agents](coding-agent-support.md).

Publication, tagging, crates.io upload, and Owner production installation
remain separate decisions after the release criteria are satisfied.
